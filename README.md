# arbiter — LLM-оркестратор над общей БД находок

🔴 Единственное место в контуре mad-tools, где языковая модель в петле. И даже здесь
она только **предлагает**, какую пробу гнать следующей. **Вердикт ставит код:** парсинг
ответа, валидацию имени инструмента против реального списка, выбор цели и код возврата.

## Использование

```
arbiter next [--json plan.json] [--model openai/gpt-4o-mini]
arbiter tools     # реальный список инструментов, которым доверяет валидатор
```

`arbiter next` читает находки из соседнего `finding-organizer` (`fo.store.list_findings`),
через один дешёвый вызов OpenRouter предлагает `next_tool`, и возвращает структурный план
`{next_tool, target, rationale}`. `next_tool` обязан быть из реального списка
(overreach, ghostwrite, needler, mcpx, spike, exhaust, collider, babel, snare, shadow,
banshee, arsenic, smuggler) — иначе прогон падает в rc=1.

## Ключ OpenRouter

Читается в память (значение не печатается): сначала `~/.config/mad/secrets.env`
(`OPENROUTER_API_KEY=…`), затем `/srv/secrets/mad/openrouter_huly.env` под `sudo`.

## Коды возврата

| rc | значение |
|----|----------|
| 0 | собран валидный план (next_tool существует) |
| 1 | модель предложила несуществующий инструмент (галлюцинация имени) |
| 2 | проверка не состоялась: нет БД / пустая БД / нет ключа / нет сети |

## Тестовая инъекция

`ARBITER_MOCK_RESPONSE=<raw>` подменяет ответ модели без сети — так проверяется
валидатор (rc=1 на выдуманном имени, rc=0 на валидном) без траты ключа.

## Чего arbiter НЕ доказывает

Что предложение модели **хорошее**. arbiter проверяет только **структуру и валидность
имени** инструмента — что план разбираем и ссылается на существующую пробу. Уместность,
приоритет и польза выбранной пробы кодом не гарантируются; это подсказка, а не решение.
